# PLC VM V1 Specification

## Purpose

This document defines a first technical specification for a PLC virtual machine
integrated into the NodeNet-SoC-RiscV platform.

The target architecture is:

- PicoRV32 remains the system orchestrator.
- A dedicated `plc_vm` HDL module executes PLC bytecode.
- SDRAM becomes a shared runtime memory accessible by the CPU and by `plc_vm`.
- The CPU loads configurations, resolves point references, links programs, loads
  bytecode into SDRAM, starts program execution, and monitors runtime state.

This V1 specification is intentionally constrained to keep the first hardware
implementation deterministic and debuggable.

## Goals

- Allow the CPU and `plc_vm` to access the same SDRAM address space.
- Define a stable binary ABI for PLC runtime data that does not depend on C++
  firmware structure layout.
- Support PLC program execution from bytecode generated by a PC toolchain.
- Support `float` values in V1.
- Support multiple PLC programs executing concurrently in V1.
- Allow the CPU to perform a link phase from symbolic point identifiers to
  runtime point indices before loading a program onto `plc_vm`.

## Non-Goals For V1

- Direct execution of C++ `PointCatalog` or `PointState` in hardware.
- Dynamic memory allocation inside `plc_vm`.
- String processing inside the VM runtime.
- JIT compilation or self-modifying code.
- Fully general multi-master cache coherency.

## Architecture Overview

The architecture is split into four layers:

1. `Shared SDRAM fabric`
2. `PLC runtime ABI`
3. `plc_vm` execution engine
4. `CPU-side loader/linker/orchestrator`

### High-Level Roles

- `PicoRV32`
  - owns flash/config/network management
  - owns point definition management
  - resolves point names to runtime indices
  - loads and links programs
  - starts and stops program slots
  - supervises diagnostics and fault reporting

- `plc_vm`
  - fetches and executes PLC bytecode from SDRAM
  - reads point values from the PLC runtime store
  - writes output values back to the PLC runtime store
  - maintains per-program execution state
  - reports faults and execution status through MMIO and SDRAM control blocks

## 1. Shared SDRAM Architecture

### 1.1 Functional Requirements

- The CPU and `plc_vm` shall see the same SDRAM address map.
- Both masters shall be able to read and write SDRAM.
- Accesses shall be arbitrated in hardware.
- The system shall preserve correctness under alternating accesses from CPU and
  `plc_vm`.
- The architecture shall support future addition of other masters without
  changing the PLC ABI.

### 1.2 Interconnect Requirements

- The current single-master CPU-to-SDRAM path shall evolve into a multi-master
  SDRAM access path.
- V1 shall support at least `2` masters:
  - `picorv32_wb`
  - `plc_vm`
- The arbitration policy shall be documented and deterministic.
- The V1 arbitration policy is `round-robin` with no permanently preferred
  master.
- The first implementation should grant at most one completed transaction per
  arbitration turn before rotating to the next requesting master.

Rationale:

- CPU-side point publication and control traffic are considered as important as
  PLC-side point consumption and execution traffic.
- Avoiding fixed priority removes one extra suspect when debugging system-level
  stalls or starvation.

### 1.3 Addressing Rules

- All masters shall use the same physical SDRAM base address.
- The PLC runtime layout shall be defined by fixed regions.
- The PLC runtime ABI shall not depend on the in-memory layout of firmware C++
  objects.

### 1.4 Recommended SDRAM Layout

The following layout is proposed inside the SDRAM window starting at
`0x2000_0000`.

| Region | Start | Size | Purpose |
| --- | --- | --- | --- |
| General firmware workspace | `0x2000_0000` | `64 KB` | CPU-only generic use |
| PLC bytecode area | `0x2001_0000` | `256 KB` | Program images for all slots |
| PLC descriptor table | `0x2005_0000` | `64 KB` | Stable point metadata |
| PLC value table | `0x2006_0000` | `64 KB` | Scalar point values |
| PLC status table | `0x2007_0000` | `64 KB` | Quality, timestamps, flags |
| Program control blocks | `0x2008_0000` | `64 KB` | Per-slot configuration and status |
| Program work area | `0x2009_0000` | `256 KB` | Per-slot stacks, timers, scratch |
| Trace and diagnostics | `0x200D_0000` | `64 KB` | Runtime traces and fault logs |

Sizes may be tuned later, but the region identities shall remain versioned.

### 1.5 Concurrency Model

V1 shall use a simple shared-memory model:

- The CPU performs load/link/configuration operations while a target program
  slot is stopped.
- A running program slot reads inputs and commits outputs through the PLC ABI.
- The CPU may inspect runtime state while programs are running.
- The CPU shall not patch active bytecode in place for a running slot.

Recommended rule for V1:

- program image update requires the target slot to be stopped
- descriptor table rebuild requires all slots to be stopped
- value/status table reads are allowed while running
- value/status writes from CPU during runtime are restricted to maintenance or
  explicit control paths

Behavior under prolonged simultaneous accesses:

- if CPU and `plc_vm` both request SDRAM continuously, the fabric shall keep
  forward progress for both masters
- no master shall starve another master under sustained load
- the first V1 target is fairness and correctness, not maximum throughput
- if throughput tuning becomes necessary later, it shall preserve the same
  observable software contract

### 1.6 Synchronization Primitives

The following minimum synchronization primitives shall exist:

- per-slot `RUN/STOP/RESET` control bits
- per-slot `CONFIG_VALID` status bit
- per-slot `FAULT` status bit
- per-slot `SCAN_DONE` latched bit
- per-slot `heartbeat/cycle_counter`
- optional global `STORE_EPOCH` counter incremented on descriptor rebuild

### 1.7 Design Constraint

V1 should keep the SDRAM sharing model simple.

The preferred approach is:

- shared SDRAM transport
- stable ABI over that transport
- no attempt to expose raw firmware structures to HDL

## 2. PLC Runtime ABI V1

### 2.1 Design Principles

- All runtime point access from `plc_vm` shall be index-based.
- Runtime indices shall be stable for the duration of a loaded PLC runtime.
- Symbolic names shall be resolved by the CPU before program start.
- The ABI shall be versioned.
- The ABI shall use fixed-size binary records.

### 2.2 Supported Value Types In V1

V1 shall support the following types inside `plc_vm`:

- `bool`
- `uint16`
- `int16`
- `uint32`
- `int32`
- `float32`

Strings are not supported inside `plc_vm` V1.

### 2.3 Point Descriptor Table

Each runtime point shall have one stable descriptor entry.

Suggested C layout:

```c
struct PlcPointDescriptorV1 {
    uint16_t point_index;
    uint8_t value_type;
    uint8_t flags;
    uint32_t value_offset;
    uint32_t status_offset;
    uint32_t reserved0;
    uint32_t reserved1;
};
```

#### Descriptor Flags

- bit `0`: readable
- bit `1`: writable
- bit `2`: input point
- bit `3`: output point
- bit `4`: internal point
- bit `5`: float point
- bit `6`: reserved
- bit `7`: reserved

### 2.4 Point Value Table

Values shall be stored in fixed-size slots.

Suggested C layout:

```c
struct PlcPointValueV1 {
    uint32_t raw0;
    uint32_t raw1;
};
```

Encoding rules:

- `bool`, `uint16`, `int16`, `uint32`, `int32` use `raw0`
- `float32` uses IEEE-754 binary32 in `raw0`
- `raw1` is reserved for future use or widened types

### 2.5 Point Status Table

Suggested C layout:

```c
struct PlcPointStatusV1 {
    uint32_t quality;
    uint32_t last_update_ms;
    uint32_t last_writer;
    uint32_t flags;
};
```

Suggested `last_writer` values:

- `0`: unknown
- `1`: CPU
- `2`: PLC VM
- `3`: fieldbus poller
- `4+`: reserved

### 2.6 ABI Version Header

Suggested C layout:

```c
struct PlcRuntimeHeaderV1 {
    uint32_t magic;
    uint16_t version;
    uint16_t flags;
    uint32_t descriptor_count;
    uint32_t descriptor_base;
    uint32_t value_base;
    uint32_t status_base;
    uint32_t store_epoch;
};
```

The CPU shall populate this header before any slot is started.

Suggested `flags` bits:

- bit `0`: shared runtime write queue available at `kPlcRuntimeWriteQueueBase`

### 2.7 Optional Runtime Write Queue

To avoid rescanning the full runtime point table when the PLC VM writes only a
small subset of points, the shared SDRAM ABI may expose a fixed-size ring queue
of runtime point indices.

Suggested C layout:

```c
struct PlcRuntimeWriteQueueV1 {
    uint32_t head;
    uint32_t tail;
    uint32_t overflow_count;
  uint32_t indices[384];
};
```

Suggested behavior:

- the queue lives in a dedicated SDRAM window owned by the runtime ABI
- the VM pushes a runtime `point_index` after publishing a point value/status
- the CPU pops queued indices and applies only those writes
- `overflow_count` increments when the producer cannot enqueue because the ring
  is full
- on overflow, writes may be dropped until the producer/consumer contract is restored

Producer ordering requirement:

- the VM shall write `value`, then `status`, then enqueue the runtime index
- `status.last_writer` shall be set to `PLC VM` before the enqueue becomes
  visible to the CPU
- the VM should enqueue a point only once while `status.last_writer` still
  equals `PLC VM`; repeated writes shall update the same runtime slot without
  duplicating queue entries

## 3. CPU Link Phase

### 3.1 Rationale

PLC source programs are expected to reference symbolic points such as:

- device identifier
- feature identifier
- point identifier

The VM shall not resolve those strings at runtime.

Instead, the CPU shall perform a link step before loading the program to a VM
slot.

### 3.2 Link Responsibilities

The CPU-side linker shall:

- load a relocatable PLC object file from flash or PC-side tooling
- parse symbol declarations and relocation records required by the program
- combine constant point symbols with load-time parameter bindings
- resolve each symbolic point reference to a runtime `point_index`
- patch relocation entries and generate a slot-ready image in SDRAM
- verify type compatibility against the runtime descriptor table
- validate that all required program parameters are present and well-typed
- keep the persistent flash artifact relocatable; only the slot image is linked
- reject a load if required points are missing or type-incompatible

### 3.3 Link Inputs

The link phase consumes:

- a compiled PLC object file stored in flash or received from the host
- a slot parameter binding block for the current program instance
- a runtime point catalog known by the CPU
- the current runtime ABI version
- the target slot configuration

### 3.4 Link Outputs

The link phase produces:

- a fully linked bytecode image with resolved point indices
- a slot control block for the target runtime slot
- a slot parameter block that records the current program instance bindings
- optional symbol debug metadata retained by the CPU

### 3.5 Stable V1 Artifact Model

The stable V1 model is a two-stage program artifact:

1. `PLC object file`
  - stored persistently in flash
  - symbolic point references still present
  - relocations still unresolved
  - symbol table and resource budgets retained

2. `PLC linked image`
  - produced only when a slot is loaded
  - written to SDRAM for execution
  - point references replaced by stable `point_index`
  - tied to the current point catalog and current slot parameters

This allows the same stored program to be re-linked against different target
point maps or different parameter bindings without recompiling it.

The repository should not keep a second persistent artifact format for already
linked images. The canonical durable artifact in V1 is the relocatable object
file.

### 3.6 Symbol Classes

V1 shall distinguish three symbol classes:

- `CONST POINT_ID`: a point path fixed in the program source
- `PARAM POINT_ID`: a point path provided when a slot instance is loaded
- local variable declarations: deferred to a later VM extension and out of scope
  for this first linker refactor

For the initial refactor, only point-symbol classes are required by the loader.

### 3.7 Acceptance Rule

A slot shall only be started if:

- the program image is linked
- the ABI version matches
- all point relocations were resolved
- all point types were validated
- the target slot state is `STOPPED` or `RESET`

## 4. Multi-Program Execution Model

### 4.1 Requirement

`plc_vm` shall support multiple PLC programs executing concurrently.

Implementation note for the current firmware-first phase:

- bare-metal firmware execution is only a validation scaffold for slot `0`
- firmware should not be generalized into a full multi-slot scheduler unless that
  work is directly needed for hardware bring-up
- the multi-slot execution target remains the HDL `plc_vm` transition

### 4.2 Slot-Based Model

V1 shall expose a slot-based execution model.

Each slot owns:

- a program image region
- a control block
- a program counter
- a stack
- timer state
- scratch state
- execution status

### 4.3 Slot Count

The architecture shall support two target capacities:

- `16 slots` as the recommended V1 implementation target
- `64 slots` as a design scalability target

Recommended interpretation:

- `16 slots` should be considered the initial hardware acceptance target
- `64 slots` should be considered an architectural maximum target if timing,
  BRAM usage, control complexity, and scan budget allow it

### 4.4 Recommendation

V1 implementation should start with `16 slots`.

Reasoning:

- much lower control complexity
- simpler debug
- lower BRAM/register pressure for per-slot state
- easier arbitration and scheduling validation
- easier PC driver/toolchain validation

The software-visible specification may still encode `64` as a maximum slot ID
range for forward compatibility, but hardware revision `v1.0` may legally
advertise a smaller implemented count.

### 4.5 Slot Scheduling

V1 scheduling shall be deterministic.

Recommended policy:

- each active slot executes one scan in round-robin order
- each slot has an instruction budget per scan
- each slot has an optional time budget per scan
- over-budget execution shall fault the slot, not the whole VM

### 4.6 Shared Point Access Between Programs

Multiple slots may access the same runtime point table.

V1 rules:

- multiple readers are allowed
- multiple writers are allowed but their behavior must be defined
- if two slots write the same point in the same scheduler epoch, V1 shall use a
  deterministic rule

Recommended first rule:

- `last committing slot in scheduler order wins`

Alternative future rules may include:

- priority-based writer selection
- explicit ownership of output points
- commit arbitration by point class

### 4.7 Slot Control Block

Suggested C layout:

```c
struct PlcProgramControlBlockV1 {
    uint32_t magic;
    uint16_t version;
    uint16_t slot_id;
    uint32_t control;
    uint32_t status;
    uint32_t pc;
    uint32_t cycle_counter;
    uint32_t fault_code;
    uint32_t fault_info;
    uint32_t bytecode_base;
    uint32_t bytecode_size;
    uint32_t stack_base;
    uint32_t stack_size;
    uint32_t timer_base;
    uint32_t timer_count;
    uint32_t max_instructions_per_scan;
    uint32_t max_scan_time_us;
    uint32_t params_base;
    uint32_t params_size;
};
```

### 4.8 Program Parameters

Program parameters are part of the loaded program instance for one slot.

Rules:

- parameters are written at load time for the currently selected program type
- parameters belong to the slot instance of that program, not to the slot as a
  persistent independent object
- loading a different program into the slot shall replace the parameter block
  and shall not preserve parameters from the previous program
- stopping or faulting a slot does not by itself redefine parameters; a new load
  operation does

For the first stable linker contract, V1 parameters are restricted to symbolic
point bindings:

- `PARAM POINT_ID <name>` declares one required symbolic point parameter
- the parameter value is a full point path of the form
  `deviceId.feature.pointId`
- the host-side assembler resolves the parameter declaration to a concrete point
  path before the object file is uploaded or stored
- the firmware loader still resolves that final point path against the current
  runtime point catalog during the slot load step
- if the path is missing, ill-formed, type-incompatible, or access-incompatible,
  the load shall fail before the slot starts

Example:

```text
PARAM POINT_ID input
CONST POINT_ID y, gb9fao5yk4f.modbus0.waveshare8ch.output4

LOAD_BOOL input
STORE_BOOL y
HALT
```

## 5. PLC Object And Bytecode V1

### 5.1 Requirements

- deterministic execution
- fixed and bounded resources
- no dynamic allocation
- fast decode in HDL
- direct indexed access to runtime points after link
- `float32` support in V1

### 5.2 Execution Model

The recommended V1 design is a small stack machine.

Each active slot executes:

1. optional input snapshot phase
2. bytecode execution phase
3. output commit phase
4. status/timestamp update phase

### 5.3 Source-Level Symbolic Syntax

The source accepted by the assembler shall separate declarations from
instructions.

Minimal V1 declaration forms:

- `CONST POINT_ID <symbol>, <deviceId.feature.pointId>`
- `PARAM POINT_ID <symbol>`

Minimal V1 instruction forms:

- `LOAD_BOOL <symbol>`
- `STORE_BOOL <symbol>`
- `HALT`

Example:

```text
PARAM POINT_ID input
CONST POINT_ID y, gb9fao5yk4f.modbus0.waveshare8ch.output4

LOAD_BOOL input
STORE_BOOL y
HALT
```

Assembly rules:

- symbol names are local to one PLC object file
- `LOAD_BOOL` and `STORE_BOOL` operands refer to symbolic point declarations,
  not to literal runtime indices
- the assembler encodes placeholder immediates in the code stream and emits
  relocation records that identify which symbol must be resolved by the loader
- literal runtime indices are not the canonical source form in stable V1

### 5.4 PLC Object File Header

Suggested V1 C layout:

```c
struct PlcObjectFileHeaderV1 {
    uint32_t magic;
    uint16_t version;
    uint16_t abi_version;
    uint32_t flags;
    uint32_t total_size;
    uint32_t code_size;
    uint32_t entry_offset;
    uint16_t symbol_count;
    uint16_t relocation_count;
    uint32_t symbol_table_offset;
    uint32_t relocation_table_offset;
    uint32_t max_instructions_per_scan;
    uint32_t max_scan_time_us;
    uint32_t runtime_header_addr;
    uint32_t object_checksum;
};
```

The persistent flash artifact is the raw object file bytes starting at this
header. No second linked-package container is kept as a durable V1 format.

### 5.5 Symbol Records

Suggested V1 C layout:

```c
enum PlcObjectSymbolKindV1 : uint8_t {
    kPlcSymbolConstPointId = 0,
    kPlcSymbolParamPointId = 1,
};

struct PlcObjectSymbolRecordV1 {
    char symbol_name[16];
    uint8_t symbol_kind;
    uint8_t expected_type;
    uint8_t access;
    uint8_t reserved0;
    PointIdentity point_id;
};
```

Rules:

- `symbol_name` stores the symbolic operand name used by instructions
- for `kPlcSymbolConstPointId`, `point_id` contains the full fixed point path
- for `kPlcSymbolParamPointId`, the current implementation also stores the bound
  full point path in `point_id` before upload
- the loader uses `symbol_kind` for diagnostics and future evolution, but both
  point-symbol kinds are currently linked from the stored `point_id` field

### 5.6 Relocation Records

Compiled PLC objects may contain unresolved symbolic point references.

Suggested C layout:

```c
struct PlcRelocationV1 {
    uint32_t instruction_offset;
    uint16_t relocation_kind;
    uint16_t symbol_index;
};
```

After CPU linking, those relocations are resolved to concrete runtime point
indices.

### 5.7 Supported Opcodes In V1

The bytecode shall support at least the following operations.

#### Control

- `NOP`
- `HALT`
- `JMP rel16`
- `JZ rel16`
- `JNZ rel16`

#### Stack

- `PUSH_U32 imm32`
- `PUSH_I32 imm32`
- `PUSH_F32 imm32`
- `DUP`
- `DROP`
- `SWAP`

#### Point access

- `LOAD_POINT idx16`
- `STORE_POINT idx16`
- `LOAD_STATUS idx16`
- `SET_QUALITY idx16, imm16`

#### Integer and boolean ops

- `EQ`
- `NE`
- `LT`
- `LE`
- `GT`
- `GE`
- `AND`
- `OR`
- `XOR`
- `NOT`
- `ADD`
- `SUB`
- `MUL`
- `DIV`
- `MOD`
- `MIN`
- `MAX`
- `CLAMP`

#### Float ops

- `FADD`
- `FSUB`
- `FMUL`
- `FDIV`
- `FEQ`
- `FNE`
- `FLT`
- `FLE`
- `FGT`
- `FGE`
- `FMIN`
- `FMAX`
- `I32_TO_F32`
- `U32_TO_F32`
- `F32_TO_I32`

#### Time and timers

- `GET_TIME_MS`
- `TON_START timer_idx16, preset_ms32`
- `TON_DONE timer_idx16`
- `TOF_START timer_idx16, preset_ms32`
- `TOF_DONE timer_idx16`

### 5.8 Float Support Notes

`float32` is required in V1.

This has direct hardware cost and must be acknowledged explicitly.

Recommended implementation options:

- Option A: dedicated float operator pipeline in HDL
- Option B: staged multi-cycle float unit integrated into `plc_vm`
- Option C: limited float op subset in first hardware release, while keeping the
  ISA stable

Recommended pragmatic choice:

- support `LOAD/STORE/PUSH_F32`
- support float compare and basic arithmetic
- keep float transcendental functions out of V1

Excluded from V1:

- `sin`, `cos`, `exp`, `log`
- mixed implicit numeric promotions beyond documented conversions

### 5.7 Type Rules

- Arithmetic opcodes shall validate operand types.
- Mixed integer/float operations shall require explicit conversion opcodes.
- A type mismatch shall fault the slot.

## 6. PLC Program Toolchain Model

### 6.1 PC-Side Toolchain

The PC-side tooling may consist of:

- a graphical PLC designer
- a compiler producing PLC object bytecode
- an optional linker-aware deployment tool

### 6.2 Recommended Artifact Chain

The recommended chain is:

1. source graph or PLC design
2. compiled PLC object
3. CPU-side link
4. linked PLC image
5. slot load and start

### 6.3 Symbol Model

The compiler shall emit symbolic references independently from target runtime
indices.

Example symbolic reference fields:

- `device_id`
- `feature_id`
- `point_id`
- expected type
- access mode

The CPU linker shall resolve those symbols against the runtime point catalog.

## 7. Diagnostics And Fault Handling

### 7.1 Fault Scope

Faults are per-slot in V1.

A slot fault shall not stop the entire `plc_vm` unless explicitly configured.

### 7.2 Minimum Fault Codes

- `0x0001` invalid opcode
- `0x0002` stack overflow
- `0x0003` stack underflow
- `0x0004` point index out of range
- `0x0005` type mismatch
- `0x0006` division by zero
- `0x0007` invalid bytecode image
- `0x0008` unresolved relocation
- `0x0009` ABI mismatch
- `0x000A` instruction budget exceeded
- `0x000B` scan time budget exceeded
- `0x000C` float unit fault

### 7.3 Diagnostics Requirements

For each slot the CPU shall be able to inspect:

- current status
- current PC
- cycle counter
- last fault code
- last fault info
- optional recent trace data

## 7.4 NodeNet Observability And Control Model

Firmware-facing PLC control should converge toward normal point features rather
than a long-lived set of dedicated service commands.

Recommended NodeNet model:

- one global feature `plc`
- one feature per slot: `plc.slot0`, `plc.slot1`, ...

The global `plc` feature should expose read-only points such as:

- implemented slot count
- active slot count
- runtime store epoch
- global fault summary

Each `plc.slotN` feature should expose read-only points such as:

- slot state
- cycle counter
- fault code
- fault info
- loaded program type
- linked bytecode size
- parameter summary

Each `plc.slotN` feature may later expose writable or command-like points for:

- start
- stop
- reset
- clear fault
- load request staging

This point-based model is preferred because:

- it aligns PLC control with the rest of the NodeNet catalog
- PLC state becomes reusable by other PLC programs through the same runtime
  point model
- one slot may eventually supervise another slot through ordinary point reads
  and writes

## 8. Acceptance Criteria

The V1 architecture is acceptable when the following are true.

### Shared SDRAM

- CPU and `plc_vm` can both read and write SDRAM
- arbitration is deterministic and free from deadlock in nominal use
- all masters observe the same address mapping

### ABI

- `plc_vm` accesses runtime points only through the documented ABI
- runtime point indices remain stable while programs are running
- the ABI is versioned and validated before slot start

### Linking

- a PLC object with symbolic point references can be linked by the CPU
- unresolved or type-incompatible references prevent slot start

### Execution

- at least one slot can execute a program reading an input and writing an output
- float values can be read, written, compared, and used in basic arithmetic
- multiple slots can run concurrently with deterministic scheduling in the HDL
  `plc_vm` phase

### Capacity

- V1 target implementation should validate `16` concurrent slots
- the architecture definition shall remain extensible toward `64` slots

## 9. Recommended First Implementation Plan

To reduce risk, the implementation should proceed in this order.

1. Add a minimal two-master SDRAM arbitration path.
2. Define and expose the PLC runtime ABI in firmware.
3. Add one-slot `plc_vm` execution prototype using the final ABI.
4. Add CPU-side link/load flow and slot metadata publication.
5. Expose PLC global and per-slot state through NodeNet point features.
6. Add HDL-side slot execution and lifecycle control.
7. Extend HDL execution to multiple slots with deterministic round-robin scheduling.
8. Add float arithmetic support if not already in the first HDL prototype.
9. Raise validated slot count toward `16`.
10. Only then evaluate practical scaling toward `64`.

## 10. Summary Of Key Decisions

- `plc_vm` V1 uses shared SDRAM, but only through a stable binary ABI.
- The CPU performs a link phase from symbolic `pointId` references to stable
  runtime `point_index` values.
- `float32` is supported in V1.
- `plc_vm` supports multiple programs through slot-based execution.
- `16 slots` is the recommended first implementation target.
- `64 slots` is a forward-looking scalability target, not the mandatory first
  silicon target.

## 11. PLC VM Technical Specification

This section defines the recommended hardware-facing technical specification for
the first `plc_vm` implementation.

### 11.1 Block Decomposition

The `plc_vm` module should be decomposed into the following sub-blocks:

- `mmio_frontend`
  - exposes configuration and status registers to the CPU
- `slot_scheduler`
  - iterates over active slots in deterministic order
- `instruction_fetch`
  - fetches bytecode words from SDRAM
- `decoder`
  - decodes opcodes and immediate operands
- `exec_core`
  - executes integer, boolean, branch, and control operations
- `float_unit`
  - executes float arithmetic and comparisons
- `point_access_unit`
  - performs value/status table reads and writes
- `timer_unit`
  - maintains per-slot TON/TOF state
- `commit_unit`
  - applies staged output writes at end of scan
- `fault_unit`
  - captures per-slot faults and halts faulty slots

### 11.2 External Interfaces

The first hardware version should expose two interfaces:

- one CPU-facing MMIO slave interface
- one SDRAM-facing master interface

Recommended interface model:

- MMIO interface on Wishbone, matching the rest of the SoC
- SDRAM access path as a Wishbone master, using the same bus family as the CPU

V1 interface choice is intentionally conservative:

- `plc_vm` should use a Wishbone-style interface consistent with the existing
  CPU-side interconnect
- this avoids introducing a second custom bus protocol as an additional debug
  surface during bring-up
- the design goal is to minimize the number of unique interconnect mechanisms
  that must be suspected in case of SDRAM access failures

### 11.3 MMIO Register Map

The MMIO register space should contain:

- one global control/status block
- one per-slot window

Suggested global register map:

| Offset | Name | Access | Description |
| --- | --- | --- | --- |
| `0x0000` | `VM_ID` | RO | implementation identifier |
| `0x0004` | `VM_VERSION` | RO | hardware version and ABI version |
| `0x0008` | `VM_CAPS` | RO | slot count, float support, timer support |
| `0x000C` | `VM_GLOBAL_CTRL` | RW | global reset, trace enable, halt all |
| `0x0010` | `VM_GLOBAL_STATUS` | RO | busy, fault summary, running slot count |
| `0x0014` | `VM_STORE_EPOCH` | RO | copied runtime store epoch |
| `0x0018` | `VM_ACTIVE_SLOT_COUNT` | RO | number of active slots |
| `0x001C` | `VM_LAST_FAULT_SLOT` | RO | slot id of last raised fault |

Suggested per-slot register window size:

- `0x40` bytes per slot minimum

Suggested per-slot register map:

| Offset | Name | Access | Description |
| --- | --- | --- | --- |
| `0x00` | `SLOT_CTRL` | RW | reset, start, stop, step, clear fault |
| `0x04` | `SLOT_STATUS` | RO | idle, running, halted, fault, config valid |
| `0x08` | `SLOT_PC` | RO | current program counter |
| `0x0C` | `SLOT_CYCLE_COUNT` | RO | completed scan counter |
| `0x10` | `SLOT_FAULT_CODE` | RO | last fault code |
| `0x14` | `SLOT_FAULT_INFO` | RO | extra fault info |
| `0x18` | `SLOT_BYTECODE_BASE` | RW | SDRAM bytecode base |
| `0x1C` | `SLOT_BYTECODE_SIZE` | RW | bytecode size |
| `0x20` | `SLOT_STACK_BASE` | RW | SDRAM or local stack base |
| `0x24` | `SLOT_STACK_SIZE` | RW | max stack capacity |
| `0x28` | `SLOT_TIMER_BASE` | RW | timer state base |
| `0x2C` | `SLOT_TIMER_COUNT` | RW | timer capacity |
| `0x30` | `SLOT_MAX_INSNS` | RW | instruction budget per scan |
| `0x34` | `SLOT_MAX_SCAN_US` | RW | time budget per scan |
| `0x38` | `SLOT_TRACE_HEAD` | RO | optional trace write pointer |
| `0x3C` | `SLOT_RESERVED` | RO/RW | reserved for future use |

### 11.4 Global Capability Register Encoding

Suggested `VM_CAPS` encoding:

- bits `7:0`: implemented slot count
- bit `8`: float unit present
- bit `9`: timer unit present
- bit `10`: trace support present
- bit `11`: staged commit supported
- bits `15:12`: arbitration model identifier
- bits `31:16`: reserved

### 11.5 Slot State Machine

Each slot should implement the following state machine:

- `RESET`
- `IDLE`
- `READY`
- `RUNNING_FETCH`
- `RUNNING_EXEC`
- `RUNNING_COMMIT`
- `HALTED`
- `FAULTED`

Required transitions:

- `RESET -> IDLE` after slot reset is complete
- `IDLE -> READY` after CPU loads valid configuration
- `READY -> RUNNING_FETCH` on start command
- `RUNNING_* -> HALTED` on stop command
- `RUNNING_* -> FAULTED` on execution fault
- `FAULTED -> IDLE` only after clear-fault and reset command

### 11.6 Scheduler Behavior

The scheduler should iterate active slots in ascending slot order.

Required behavior:

- exactly one slot owns the execution core at a time
- each runnable slot receives at most one scan per scheduler round
- a halted or faulted slot is skipped
- a scan budget violation faults only the current slot

Recommended first implementation:

- one shared execution core
- one shared float unit
- one slot context save/restore path

This is slower than one-core-per-slot but dramatically simpler and more likely
to close timing.

### 11.7 Slot Context

Per-slot context should include:

- `pc`
- `stack pointer`
- `stack depth`
- `cycle counter`
- `instruction counter`
- `fault code`
- `fault info`
- timer state pointers or timer counters
- pending output commit count
- last scan start time

Recommended storage split:

- critical scheduler state in registers or BRAM
- deeper stack and timer tables in BRAM first, SDRAM only if required later

### 11.8 Stack Model

The VM should use a typed logical stack with fixed-width physical entries.

Suggested stack entry layout:

```c
struct PlcVmStackEntryV1 {
    uint32_t value;
    uint8_t type;
    uint8_t flags;
    uint16_t reserved;
};
```

Type tags:

- `0`: invalid
- `1`: bool
- `2`: uint16
- `3`: int16
- `4`: uint32
- `5`: int32
- `6`: float32

V1 requirement:

- all binary operators validate operand type tags
- no implicit widening except through explicit conversion opcodes

### 11.9 Point Access Semantics

The point access unit should support the following operations:

- load current point value by `point_index`
- store staged output value by `point_index`
- load point status by `point_index`
- write point quality or flags by `point_index`

Recommended V1 write discipline:

- input points are read-only for `plc_vm`
- output points are writable by `plc_vm`
- internal points are read/write
- direct write attempts to non-writable points fault the slot

### 11.10 Commit Model

V1 should use staged writes and end-of-scan commit.

Required behavior:

- `STORE_POINT` records a pending write in slot-local state
- the pending write is not visible until commit phase
- commit occurs after successful scan completion
- if a scan faults, pending writes from that scan are discarded

Rationale:

- deterministic scan semantics
- simpler debugging
- avoids partially applied output state on slot faults

### 11.11 Float Unit Behavior

The float unit must support at minimum:

- load/store of `float32`
- `FADD`, `FSUB`, `FMUL`, `FDIV`
- `FEQ`, `FNE`, `FLT`, `FLE`, `FGT`, `FGE`
- `I32_TO_F32`, `U32_TO_F32`, `F32_TO_I32`

Recommended behavior:

- float operations are multi-cycle
- the scheduler stalls the active slot while the float unit is busy
- float exceptions should map to a per-slot VM fault code

Possible implementation source for V1:

- `dawsonjon/verilog-math` is a plausible candidate for the `float_unit`
  because it provides synthesizable IEEE-754 Verilog floating-point blocks,
  pipelined implementations, and the core operations required by `plc_vm` V1.

Selection criteria before adoption:

- verify single-precision `float32` coverage for all required opcodes
- confirm integration cost on ECP5 resource and timing budgets
- confirm wrapper simplicity for multi-cycle VM execution
- confirm behavior for `NaN`, `Inf`, denormals, and conversion edge cases

### 11.12 Timer Unit

The timer unit should support per-slot software-visible logical timers.

Minimum timer features:

- monotonic base time input in milliseconds
- TON start and done query
- TOF start and done query
- one timer state entry addressable by `timer_idx`

Suggested timer state layout:

```c
struct PlcVmTimerStateV1 {
    uint32_t start_time_ms;
    uint32_t preset_ms;
    uint8_t mode;
    uint8_t active;
    uint8_t done;
    uint8_t reserved;
};
```

### 11.13 Trace And Debug

Trace support is optional but strongly recommended.

If implemented, each slot should be able to emit compact trace events such as:

- slot start
- slot stop
- branch taken
- point load
- point store
- fault raised

Recommended trace format:

- fixed-size `8-byte` or `16-byte` events
- timestamp or cycle count
- slot id
- event id
- argument field

Phase 1 and bring-up debug policy:

- expose as many useful status and sticky debug signals as practical
- prefer explicit counters and latched fault/status bits over inferred behavior
- keep CPU-readable visibility so firmware can summarize failures on the OLED

Recommended minimum observability for shared SDRAM bring-up:

- last granted master id
- grant counters per master
- outstanding request indicator per master
- per-master stall counters
- arbitration state
- timeout flags
- SDRAM response error flags
- optional last failing address capture

### 11.14 Reset Behavior

Global reset should:

- stop all slots
- clear scheduler state
- clear fault summary
- preserve SDRAM runtime data unless explicitly requested otherwise

Slot reset should:

- clear slot-local context
- clear pending writes
- clear slot fault state
- preserve bytecode region loaded by CPU

## 12. Implementation Plan

This section provides a staged implementation plan intended to be followed in
the repository.

### 12.1 Phase 0: Freeze Contracts

Objective:

- stabilize the software-visible contracts before RTL expansion

Tasks:

1. Freeze this specification for ABI v1, bytecode v1, and slot control model.
2. Freeze the first supported numeric types, including `float32`.
3. Freeze the first slot target count as `16` implemented slots.
4. Freeze the first conflict rule for multi-writer outputs.
5. Freeze `Wishbone` as the V1 bus family for `plc_vm` external access.
6. Freeze `round-robin` as the V1 SDRAM arbitration policy.
7. Freeze immediate FPGA validation as the primary bring-up target.

Exit criteria:

- document reviewed and accepted
- no open ambiguity on ABI layout, slot model, or link phase

Frozen V1 decisions:

- `plc_vm` uses Wishbone-compatible interfaces for MMIO and SDRAM master access
- the shared SDRAM fabric uses round-robin arbitration without fixed master
  priority
- prolonged simultaneous requests must preserve fairness and forward progress
- debug visibility is designed in from the first shared-SDRAM revision
- first validation target is the real FPGA platform, not simulation-only

### 12.2 Phase 1: Shared SDRAM Fabric

Objective:

- allow CPU and `plc_vm` to access the same SDRAM safely

Reference design note:

- see `Documentation/plc_vm_step1_shared_sdram.md`

Tasks:

1. Introduce a minimal two-master Wishbone arbitration block between SDRAM and
  masters.
2. Keep PicoRV32 path behavior unchanged for existing firmware execution.
3. Define the second master interface so it matches the future `plc_vm`
  Wishbone-style access model.
4. Add a dummy second master test path that can perform controlled reads and
  writes.
5. Implement strict round-robin fairness for concurrently requesting masters.
6. Add debug counters and sticky flags for grant, stall, timeout, arbitration
  state, and response errors.
7. Expose enough debug state for firmware to summarize faults on the OLED.

Validation:

1. CPU-only regression still boots and runs from SDRAM.
2. Dummy second master can read/write reserved SDRAM locations.
3. No deadlock under alternating traffic.
4. No starvation under sustained dual-master traffic.
5. Debug counters and sticky flags react as expected on hardware.

Exit criteria:

- two-master SDRAM access validated on the FPGA hardware target

### 12.3 Phase 2: Firmware Runtime ABI Publisher

Objective:

- make firmware publish a PLC runtime store independent from C++ layout

Tasks:

1. Define firmware-side packed structs matching the ABI.
2. Build a runtime point index table in firmware.
3. Export descriptor, value, and status regions into reserved SDRAM windows.
4. Add an epoch counter incremented on full descriptor rebuild.
5. Keep existing `PointCatalog` as source of truth initially.

Validation:

1. Firmware can rebuild ABI tables deterministically.
2. A debug dump can show descriptor/value/status contents.
3. Existing point polling still works.

Exit criteria:

- firmware publishes a stable PLC ABI image in SDRAM

### 12.4 Phase 3: CPU Linker And Loader

Objective:

- let the CPU load relocatable PLC objects and produce slot-ready images

Tasks:

1. Finalize the V1 PLC object file format as the only durable deployment
  artifact.
2. Implement point symbol resolution by `device_id/feature/point_id`.
3. Implement load-time resolution of `PARAM POINT_ID` bindings.
4. Implement type validation against the descriptor table.
5. Patch relocations to `point_index` values.
6. Write linked images and slot control blocks into SDRAM.

Validation:

1. Missing point references are rejected.
2. Type mismatches are rejected.
3. The same object can be linked twice against changed point maps.

Exit criteria:

- CPU can produce a linked slot image without RTL execution support yet

### 12.5 Phase 4: Single-Slot VM Prototype

Objective:

- validate the instruction fetch/decode/execute path on a minimal slot count

Tasks:

1. Implement MMIO global block and slot `0` window.
2. Implement one execution core with integer and branch opcodes first.
3. Implement `LOAD_POINT` and staged `STORE_POINT`.
4. Implement commit-on-scan-complete.
5. Implement per-slot faults and stop behavior.

Validation:

1. A minimal program can mirror an input point into an output point.
2. An invalid opcode faults slot `0`.
3. A faulted scan does not partially commit outputs.

Exit criteria:

- one program executes end-to-end through the SDRAM ABI

### 12.6 Phase 5: Float Support

Objective:

- add `float32` execution support while keeping the scheduler deterministic

Tasks:

1. Implement `PUSH_F32`, float load/store, and float compares.
2. Implement `FADD`, `FSUB`, `FMUL`, `FDIV`.
3. Implement explicit conversion opcodes.
4. Define fault behavior for invalid float operations.

Validation:

1. A float threshold program executes correctly.
2. Float compare and conversion edge cases are covered in simulation.
3. Mixed integer/float without explicit conversion faults as expected.

Exit criteria:

- float path functionally validated

### 12.7 Phase 6: Multi-Slot Scheduler

Objective:

- extend the single execution engine to multiple runnable programs

Tasks:

1. Generalize slot control blocks to `N` slots.
2. Add per-slot context storage.
3. Implement deterministic round-robin scheduling.
4. Add per-slot instruction and time budgets.
5. Add multi-writer output commit rule.

Validation:

1. Multiple simple programs execute concurrently.
2. A fault in one slot does not stop healthy slots.
3. Output conflicts follow the documented deterministic rule.

Exit criteria:

- at least `4` slots stable in simulation, then raised toward `16`

### 12.8 Phase 7: Toolchain Integration

Objective:

- connect PC-side design tools to the CPU linker/loader flow

Entry gate:

- defer the NodeNet deployment transport until after phase 4 validates that one
  minimal program really runs end-to-end on slot `0`

Tasks:

1. Define the PLC object file emitted by the compiler/assembler.
2. Define declaration syntax for `CONST POINT_ID` and `PARAM POINT_ID`.
3. Define the deployment protocol to send PLC object files to the CPU.
4. Add debug symbol retention for diagnostics.
5. Add version checks for compiler output vs ABI/VM hardware.

Validation:

1. A program compiled on PC can be linked and loaded by firmware.
2. ABI and bytecode version mismatches are rejected cleanly.

Exit criteria:

- end-to-end PC to CPU to `plc_vm` program deployment works

### 12.8 Phase 8: NodeNet PLC Upload Transport

Objective:

- add remote deployment of raw PLC objects over NodeNet only after slot `0`
  execution is already validated locally

Tasks:

1. Define a chunked NodeNet upload session for raw PLC object bytes.
2. Stage received object bytes into the dedicated raw PLC flash slot.
3. Verify size and checksum before CPU-side link.
4. Resolve slot parameter bindings and perform CPU-side link from raw object
  flash staging into a slot-ready SDRAM image.
5. Expose slot load and fault status through NodeNet responses.

Validation:

1. A PLC object larger than one NodeNet frame can be uploaded reliably.
2. Corrupted or truncated uploads are rejected cleanly.
3. A valid upload ends with a loaded slot image identical to local deployment.

Exit criteria:

- NodeNet can deploy a PLC object into flash, link it, and arm a runtime slot

### 12.9 Phase 9: Scale To 16 Slots

Objective:

- reach the recommended V1 slot target

Tasks:

1. Measure scheduler throughput and SDRAM pressure.
2. Tune stack/timer/context storage placement.
3. Reduce unnecessary SDRAM round-trips where possible.
4. Validate worst-case scan latency.

Validation:

1. `16` slots can be configured and run under representative traffic.
2. Scan budgets remain deterministic.
3. Fault handling remains isolated per slot.

Exit criteria:

- `16` implemented slots validated as the first official platform target

### 12.10 Phase 10: Evaluate 64-Slot Scalability

Objective:

- decide whether `64` slots is practical with the same architectural model

Tasks:

1. Measure BRAM, LUT, and timing headroom.
2. Measure arbitration contention with many active slots.
3. Evaluate whether some per-slot state must move to SDRAM.
4. Evaluate whether one shared execution core remains acceptable.

Decision outputs:

- retain `16` as hardware limit, or
- raise to a higher validated limit, or
- define `64` as a later hardware revision target

### 12.11 Repository Documentation Follow-Up

When implementation starts, the repository documentation should gain:

1. a memory map page for PLC runtime regions
2. a bytecode format page
3. an MMIO register page for `plc_vm`
4. a firmware linker/loader page
5. a simulation and validation checklist for each phase
